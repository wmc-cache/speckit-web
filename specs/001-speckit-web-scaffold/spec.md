# Feature Specification: Spec Kit Web 文档查看与项目初始化开源脚手架

**Feature Branch**: `001-speckit-web-scaffold`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "帮我写一个基于Spec Kit 的web 文档查看和Spec Kit项目初始化github 开源脚手架"

## Clarifications

### Session 2026-10-23

- Q: 文档查看器应该以什么形态运行？ → A: 本地启动 + 静态站点发布都支持：本机一条命令启动查看本地项目（实时刷新），同时可把文档构建为静态网站发布（如 GitHub Pages）供团队在线访问。
- Q: Spec Kit 项目初始化的入口应该是什么形式？ → A: 命令行 + 网页向导都提供：命令行交互式初始化，同时在本地模式的查看器网页中提供引导式向导。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在浏览器中浏览 Spec Kit 项目文档 (Priority: P1)

一位采用 Spec Kit 做规范驱动开发的开发者，项目里已经积累了准则（constitution）、多个特性目录（`specs/NNN-名称/`）以及其中的规范、方案、任务、检查清单等 Markdown 文档。他们希望不打开编辑器、不在文件树里来回翻找，就能在浏览器里以排版良好的形式按“特性 → 文档”的结构浏览全部内容，并能把页面分享给不熟悉命令行的产品或评审同事查看。

**Why this priority**: 文档查看是本脚手架最核心的价值，也是用户描述中的第一个关键词；只要这一项可用，就已经是可独立交付的 MVP。

**Independent Test**: 准备一个包含准则和至少两个特性（各含 spec/plan/tasks/checklists）的示例 Spec Kit 项目，用本工具打开，确认所有文档都能按结构列出并正确渲染。

**Acceptance Scenarios**:

1. **Given** 一个已初始化的 Spec Kit 项目且包含 3 个特性目录，**When** 用户打开查看器，**Then** 左侧导航按编号顺序列出 3 个特性，并单独列出项目准则入口。
2. **Given** 用户选中某个特性，**When** 查看该特性，**Then** 显示其下所有已生成的文档（规范、方案、研究、数据模型、接口契约、快速上手、任务、检查清单），未生成的标准文档显示为“未生成”而不是报错。
3. **Given** 一篇包含表格、代码块、任务复选框和相对链接的文档，**When** 用户打开它，**Then** 表格、代码块、复选框状态均正确渲染，点击指向项目内其它文档的相对链接可直接跳转到对应文档。
4. **Given** 一篇较长的文档，**When** 用户打开它，**Then** 页面提供按标题生成的目录大纲，点击可定位到对应章节。

---

### User Story 2 - 一眼看清每个特性的推进进度 (Priority: P2)

团队负责人想快速知道每个特性走到了 Spec Kit 流程的哪一步（准则 → 规范 → 澄清 → 方案 → 检查清单 → 任务 → 分析 → 实现），任务完成了多少，还有多少待澄清项，而不必逐个打开文档去数复选框。

**Why this priority**: 进度总览把“看文档”升级为“看项目状态”，是区别于普通 Markdown 浏览器的关键能力，但依赖 US1 的文档识别能力。

**Independent Test**: 在示例项目中让一个特性只有 spec.md、另一个特性有完整产物且 tasks.md 中 10 个任务完成 4 个，打开总览确认两者阶段和完成比例显示正确。

**Acceptance Scenarios**:

1. **Given** 某特性只有规范文档，**When** 用户查看项目总览，**Then** 该特性显示处于“规范”阶段，后续阶段显示为未开始。
2. **Given** 某特性的任务清单共 10 项、已勾选 4 项，**When** 用户查看该特性，**Then** 显示任务完成度 4/10（40%），并可按阶段（Phase）和用户故事分别查看完成情况。
3. **Given** 规范中仍有 2 处待澄清标记，**When** 用户查看该特性，**Then** 显示“待澄清 2 处”，点击可定位到每一处标记。
4. **Given** 某特性的检查清单共 16 项、已勾选 16 项，**When** 用户查看该特性，**Then** 该检查清单显示为“已全部通过”。

---

### User Story 3 - 快速初始化一个新的 Spec Kit 项目 (Priority: P2)

一位第一次接触 Spec Kit 的开发者希望通过简单的引导完成项目初始化：选择要使用的 AI 编程助手、脚本类型、特性编号方式和目标目录，然后得到一个可直接使用 `/speckit-*` 命令的项目，并且初始化完成后能立即在查看器中看到这个新项目。

**Why this priority**: 初始化是用户描述中的第二个关键词，能显著降低新用户上手门槛；但已有 Spec Kit 项目的用户不依赖它，因此排在文档查看之后。

**Independent Test**: 在一个空目录中按引导完成初始化，确认生成的项目结构与官方 Spec Kit 初始化结果一致，并能被查看器识别。

**Acceptance Scenarios**:

1. **Given** 一个空目录且本机满足前置条件，**When** 用户通过初始化入口选择 AI 助手与脚本类型并确认，**Then** 目录中生成标准的 Spec Kit 项目结构，并展示下一步该执行的命令。
2. **Given** 目标目录非空或已是 Spec Kit 项目，**When** 用户发起初始化，**Then** 系统明确提示风险并列出将被新增/覆盖的内容，只有在用户二次确认后才继续，绝不静默覆盖。
3. **Given** 本机缺少初始化所需的前置条件，**When** 用户发起初始化，**Then** 系统指出缺少什么以及如何安装，而不是给出难以理解的错误。
4. **Given** 初始化成功，**When** 用户选择“打开查看器”，**Then** 查看器直接打开该新项目并显示准则与空的特性列表。

---

### User Story 4 - 在文档间搜索与交叉跳转 (Priority: P3)

评审者在看任务清单时想知道某个任务对应的是哪条功能需求，或者想在整个项目里搜索某个关键词（例如“登录”）出现在哪些文档里。

**Why this priority**: 提升大型项目的查阅效率，但没有它前三个故事仍然完整可用。

**Independent Test**: 在示例项目中搜索一个仅出现在两个特性文档中的关键词，确认结果准确；点击文档中的需求编号确认跳转正确。

**Acceptance Scenarios**:

1. **Given** 项目中有多个文档包含关键词“登录”，**When** 用户在搜索框输入“登录”，**Then** 列出所有命中文档及命中位置的上下文片段，点击可跳转并高亮命中处。
2. **Given** 任务描述中引用了 `FR-003`，**When** 用户点击该编号，**Then** 跳转到同一特性规范中 FR-003 所在位置。

---

### User Story 5 - 作为 GitHub 开源项目被复用和参与 (Priority: P3)

其他开发者在 GitHub 上发现本项目，希望能按 README 在几分钟内跑起来看到效果，能把它用在自己的 Spec Kit 项目上，也能按贡献指南提交改进。

**Why this priority**: 决定项目能否作为开源脚手架被传播和维护，但不影响核心功能本身。

**Independent Test**: 让一位未参与开发的人只依据 README，从零开始完成“获取项目 → 打开内置示例项目 → 指向自己的项目”的全过程。

**Acceptance Scenarios**:

1. **Given** 一位新访客打开仓库主页，**When** 按 README 的快速开始操作，**Then** 能在 5 分钟内在浏览器里看到内置示例项目的文档。
2. **Given** 一位贡献者提交了改动，**When** 发起合并请求，**Then** 仓库的自动检查会运行并给出通过/失败结果，且有合并请求模板指引其填写说明。
3. **Given** 一位用户想基于本项目创建自己的版本，**When** 使用 GitHub 的模板/复刻功能，**Then** 得到可直接运行的完整副本。

---

### Edge Cases

- 目录中没有 `.specify/` 或 `specs/`（不是 Spec Kit 项目）时：本地模式提示“未检测到 Spec Kit 项目”并引导进入初始化向导；静态构建则直接报错退出并说明原因。
- 静态站点中的文档链接指向未被打包的文件（如源代码）时：显示为不可用链接并提示“该文件未发布”，而不是跳到 404。
- 静态站点部署在子路径下（如 `用户名.github.io/仓库名/`）时：所有页面、链接和资源仍能正常访问。
- 项目准则仍是未填写的模板占位内容时：标记为“未填写”，并提示运行准则步骤。
- 特性目录使用时间戳编号（如 `20260319-143022-名称`）或编号不连续时：仍能正确识别并按时间/编号排序。
- 文档格式有误（未闭合代码块、表格列数不一致）时：尽力渲染，不导致整个页面崩溃。
- 单个文档非常大（如超过 1 MB）时：仍可打开，必要时分段加载并给出提示。
- 用户查看期间文档在磁盘上被修改、新增或删除时：页面自动反映变化；当前打开的文档被删除时给出提示。
- 项目路径包含空格、中文或其它非 ASCII 字符时：可正常识别与显示。
- 文档中的链接或符号链接指向项目目录之外时：不得读取或展示项目目录外的文件内容。
- 项目中存在 `.env`、`.git/` 等敏感或无关目录时：不在查看器中暴露。
- 初始化过程中断（网络失败、用户取消）时：不留下半成品，或明确告知需清理的内容。
- 查看器默认使用的访问端口被占用时：自动选择其它可用端口并告知用户实际地址。

## Requirements *(mandatory)*

### Functional Requirements

**文档查看**

- **FR-001**: 系统 MUST 识别 Spec Kit 项目结构（`.specify/` 与 `specs/` 目录），列出所有特性目录，支持顺序编号与时间戳编号两种命名方式，并按编号排序。
- **FR-002**: 系统 MUST 在每个特性下展示其全部标准产物：规范（spec）、方案（plan）、研究（research）、数据模型（data-model）、接口契约（contracts/ 下所有文件）、快速上手（quickstart）、任务（tasks）、检查清单（checklists/ 下所有文件）；缺失的标准产物显示为“未生成”。
- **FR-003**: 系统 MUST 展示项目准则文档及其版本、批准日期、最后修订日期；准则仍为模板占位内容时标记为“未填写”。
- **FR-004**: 系统 MUST 将 Markdown 渲染为易读页面，至少支持标题、列表、表格、代码块（含语法高亮）、引用、任务复选框、链接和内嵌图表代码块。
- **FR-005**: 系统 MUST 为每篇文档生成基于标题的目录大纲，并支持通过地址直接定位到某篇文档的某个章节（便于分享链接）。
- **FR-006**: 文档内指向项目内其它文档的相对链接 MUST 在查看器内跳转到目标文档。
- **FR-007**: 查看器的文档浏览功能 MUST 为只读：不得修改、新建或删除项目中的任何文件；唯一的写入例外是用户在网页向导中明确确认后执行的项目初始化（见 FR-020）。
- **FR-008**: 系统 MUST 只读取项目目录内的文件，拒绝访问项目目录外的路径（包括通过 `..` 和符号链接），且默认不暴露 `.git/`、`.env` 等敏感文件。
- **FR-009**: 系统 MUST 同时提供两种查看形态：（a）本地模式——在本机以一条命令启动，查看指定目录下的 Spec Kit 项目；（b）静态发布模式——把项目文档构建为不依赖后台服务的静态网站，可直接部署到 GitHub Pages 等静态托管服务。两种形态的浏览、进度总览、搜索与交叉跳转体验一致。
- **FR-010**: 静态发布模式 MUST 只包含 Spec Kit 相关文档（准则与 `specs/` 下的产物），不得把源代码、`.git/`、`.env` 等其它文件打包进站点；仓库 MUST 提供一份开箱即用的自动发布配置示例，使用户推送文档后即可自动更新在线站点。
- **FR-011**: 在本地模式下，文档在磁盘上发生变化后，页面 MUST 在无需手动刷新的情况下自动更新。

**进度总览**

- **FR-012**: 系统 MUST 为每个特性判定其所处的流程阶段（准则、规范、澄清、方案、检查清单、任务、分析、实现），判定依据为对应产物是否存在及其内容（如规范中是否已有澄清记录、任务是否已开始勾选）。
- **FR-013**: 系统 MUST 统计任务清单的总数与已完成数，并支持按阶段（Phase）和用户故事分组展示完成度。
- **FR-014**: 系统 MUST 统计每份检查清单的总项数与已勾选数。
- **FR-015**: 系统 MUST 统计规范中剩余的待澄清标记数量，并可逐一定位。
- **FR-016**: 系统 MUST 提供项目总览页，以列表形式同时展示所有特性的阶段、任务完成度和待澄清数量。
- **FR-017**: 系统 MUST 从规范中提取用户故事及其优先级、功能需求编号、成功标准编号，并在特性页中以结构化摘要展示。

**搜索与导航**

- **FR-018**: 用户 MUST 能在整个项目的文档中进行全文搜索，结果显示所属特性、文档和命中位置的上下文片段。
- **FR-019**: 文档中出现的 `FR-###`、`SC-###`、`T###`、`CHK###` 等编号 MUST 可点击，跳转到同一特性内该编号的定义处。

**项目初始化**

- **FR-020**: 系统 MUST 同时提供两种初始化入口：（a）命令行——一条命令启动交互式问答，也支持通过参数一次性给出全部选项以便脚本化与持续集成场景使用；（b）网页向导——在本地模式的查看器中提供分步引导，当打开的目录未检测到 Spec Kit 项目时主动提示使用。静态发布模式下不提供初始化入口。两种入口的可选项、校验规则和生成结果一致。
- **FR-021**: 初始化时用户 MUST 能选择：目标目录（新建目录或当前目录）、AI 编程助手（官方 Spec Kit 支持的列表）、脚本类型（sh / PowerShell）、特性编号方式（顺序 / 时间戳）；每项都有合理默认值。
- **FR-022**: 初始化前系统 MUST 检查前置条件，缺失时说明缺什么以及如何安装。
- **FR-023**: 目标目录非空或已是 Spec Kit 项目时，系统 MUST 列出将新增或覆盖的内容并要求用户明确确认，不得静默覆盖。
- **FR-024**: 初始化生成的项目 MUST 与官方 Spec Kit 初始化结果一致，可直接被官方 `/speckit-*` 命令使用。
- **FR-025**: 初始化成功后系统 MUST 展示后续步骤指引（如先建立准则、再写规范），并提供直接在查看器中打开该项目的入口。
- **FR-026**: 初始化失败或被取消时，系统 MUST 不留下半成品文件，或明确列出需要用户清理的内容。

**开源脚手架**

- **FR-027**: 仓库 MUST 包含：说明文档（含快速开始、功能截图、使用方式）、开源许可证、贡献指南、行为准则、问题与合并请求模板、版本变更记录。
- **FR-028**: 仓库 MUST 内置一个示例 Spec Kit 项目，使用户无需准备自己的项目即可体验全部查看功能。
- **FR-029**: 仓库 MUST 配置自动化检查，在每次合并请求时运行测试并报告结果。
- **FR-030**: 仓库 MUST 可通过 GitHub 模板或复刻功能直接得到可运行的完整副本；同时支持以一条命令在任意 Spec Kit 项目上启动，无需复制本仓库。
- **FR-031**: 界面 MUST 支持简体中文与英文，默认跟随系统语言，并可手动切换。
- **FR-032**: 界面 MUST 支持浅色与深色主题，默认跟随系统设置。

### Key Entities *(include if feature involves data)*

- **Spec Kit 项目**: 一个包含 `.specify/` 配置的目录；属性包括项目名称、路径、所用 Spec Kit 版本、AI 助手、脚本类型、编号方式；包含一份准则和若干特性。
- **准则（Constitution）**: 项目级原则文档；属性包括版本、批准日期、最后修订日期、是否已填写。
- **特性（Feature）**: `specs/` 下的一个目录；属性包括编号、短名称、当前阶段、所含产物；与项目是多对一关系。
- **文档产物（Artifact）**: 特性内的一份文档；属性包括类型（规范/方案/任务/检查清单等）、路径、标题大纲、最后修改时间。
- **任务（Task）**: 任务清单中的一项；属性包括编号、是否完成、是否可并行、所属阶段、关联用户故事。
- **检查项（Checklist Item）**: 检查清单中的一项；属性包括编号、是否勾选、所属清单。
- **需求 / 成功标准（Requirement / Success Criterion）**: 规范中带编号的条目；属性包括编号、内容，可被任务和其它文档引用。
- **初始化选项（Init Options）**: 一次初始化的用户选择；包括目标目录、AI 助手、脚本类型、编号方式。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新访客仅依据 README，从获取项目到在浏览器中看到内置示例项目文档，用时不超过 5 分钟。
- **SC-002**: 用户在已有 Spec Kit 项目上通过一条命令启动查看，从执行命令到看到项目总览不超过 10 秒。
- **SC-003**: 在包含 50 个特性、共 500 篇文档的项目中，切换打开任意文档的等待时间不超过 1 秒，全文搜索结果在 1 秒内出现。
- **SC-004**: 本地模式下，文档在磁盘上修改后，页面在 2 秒内反映变化。
- **SC-005**: 使用仓库提供的自动发布配置，用户从推送文档到在线站点更新完成不超过 5 分钟（不计托管平台排队时间），且首次配置在线发布不超过 10 分钟。
- **SC-006**: 进度总览中的任务完成数、检查清单勾选数、待澄清数量与人工逐项清点结果 100% 一致。
- **SC-007**: 官方 Spec Kit 当前版本生成的所有标准产物类型 100% 能被识别并正确渲染。
- **SC-008**: 新用户无论通过命令行还是网页向导，完成一次项目初始化都不超过 2 分钟（不含下载时间），生成的项目可 100% 直接运行官方 `/speckit-*` 命令。
- **SC-009**: 在可用性测试中，至少 90% 的首次使用者无需帮助即可在 1 分钟内找到指定特性的任务完成度。
- **SC-010**: 安全测试中，通过任何路径构造方式均无法读取项目目录外的文件；查看器运行期间项目文件被修改的次数为 0。

## Assumptions

- 以 GitHub 官方 Spec Kit（github/spec-kit）当前 1.x 版本的目录与文档约定为准；官方后续调整约定时通过版本更新跟进。
- 初始化能力复用官方 Spec Kit 的初始化流程与模板，而不是自行维护一套模板，以保证生成结果与官方一致；首次初始化需要联网。
- 查看器只负责“看”，文档的编辑和 `/speckit-*` 步骤的执行仍在编辑器或 AI 编程助手中完成，不在本次范围内。
- 查看本地项目时不需要账号登录；本地模式默认只允许本机访问。静态站点的访问权限由用户选择的托管平台控制，本项目不做额外鉴权。
- 开源许可证默认采用 MIT。
- 主要面向桌面浏览器；移动端保证可阅读，不做专门优化。
- 一次查看一个 Spec Kit 项目；同时管理多个项目不在本次范围内。
- 目标用户熟悉基本的命令行操作。
